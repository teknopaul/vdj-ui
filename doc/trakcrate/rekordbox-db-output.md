# Writing rekordbox pendrives (study)

Feature name: **trakcrate** (the local library and exporter; see `trakcrate-db-format.md`). "rekordbox" below only names the third-party file format we read and write.

Goal: given a folder of `.wav` / `.mp3` files, produce a rekordbox-format export (`PIONEER/` + `Contents/`) that CDJ/XDJ players accept.
Status: **study only, nothing implemented.** This file records what we know, what we must still learn, and the plan.

Not yet for a full export, but close for a minimal one.

## Layout to produce

```
<out>/
  PIONEER/
    rekordbox/export.pdb        main DB, 4096-byte pages
    rekordbox/exportExt.pdb     extended DB (tags, etc.), 73 KB in the 7-track sample
    rekordbox/RBFLTR.DAT        232 bytes
    USBANLZ/Pxxx/yyyyyyyy/ANLZ0000.DAT|.EXT   one dir per track; xxx = partition (3 hex), y = slot (8 hex), see usbanalz-hashing.md
    USBANLZ/USBMNG.DAT          400 KB in the sample
    Artwork/NNNNN/aID.jpg       optional
    DEVSETTING.DAT, MYSETTING.DAT, djprofile.nxs   settings, ~140-160 bytes each
  Contents/<artist>/<album>/file.mp3
```

**Layout is rekordbox's, always (implemented).** An export writes `Contents/<artist>/<album>/<file>` from the track's tags, whatever the library's own folders are called (the library is never changed; there is no other layout for Pioneer drives). Names follow rekordbox, measured on the 2195 tracks of a real export (2184 exact, the rest differ only in letter case, where rekordbox reuses the first spelling because FAT folders are case insensitive): `\ / : * ? " < > |` become `_`, at most 48 characters, trailing spaces dropped, a final `.` becomes `_` (`K.O.` is `K.O_`), no artist or album is `UnknownArtist` / `UnknownAlbum`. `rekordboxFolderName` (C++) and `tc_rb_folder_name` (C). The `Pxxx` number of the analysis folder is at most 0x7F and the 8 digit number below 200003 in every real track; ours are computed with rekordbox's own rule (`usbanalz-hashing.md`: slot = hash of the path mod 200003, partition = seven slot bits) and `USBANLZ/USBMNG.DAT` is written empty, as rekordbox does when no paths collide.

The track row stores `file_path` (e.g. `/Contents/Intapol/UK Dembow/x.mp3`) and `analyze_path` (`/PIONEER/USBANLZ/P004/00028148/ANLZ0000.DAT`). The ANLZ dir name is a function of the `file_path` string alone: slot = `h mod 200003` with `h = h*0x34F5501D + c*0x93B6` (32 bit, UTF-16 units, start 0), partition = slot bits 0,2,6,7,9,13,16, `ANLZ<n>` = collision counter. The decks recompute it, so it must be exact (`usbanalz-hashing.md`).

## `export.pdb` as understood

- Page 0 is the header: page size `0x1000`, `num_tables` (20 in both samples), `next_unused_page`, unknown (5), sequence counter, then 16-byte table entries `{type, empty_candidate, first_page, last_page}`.
- Each table is a linked chain of pages: a first "index" page with flag `0x64`/`0x36`-style bits, then data pages. In the 7-track sample, page flags observed: `0x00` (10 free pages), `0x24`, `0x34`, `0x64`. The meaning of each is **not documented**; needs the kaitai spec.
- Data page: 40-byte header, row heap, and at the end row-offset groups of 16 (`0x24` bytes each: 16 u16 offsets plus a presence bitmap). Parser: `pdb.c:151-180`.
- Strings: DeviceSQL encoding (short ASCII with length byte, `0x40` long ASCII, `0x90` UTF-16LE). Parser: `pdb.c:26-50`. The writer must pick the encoding by content.
- Track row: 94 fixed bytes then 21 u16 string offsets (`pdb.c:79`). Fields are listed in `pdb.h` (`pdb_track_t`). Unknown fields must be copied from a real row as a template.
- Table type numbers: 0 tracks, 1 genres, 2 artists, 3 albums, 4 labels, 5 keys, 6 colors, 7 playlist tree, 8 playlist entries, 11/12 history, 13 artwork; tables 9, 10, 14-19 exist in the header and must be present even when empty (their layout is unknown to us).

## Design: tmpfs build, single write

The player-side concern is the one in the prompt: rekordbox does many small writes while building, which is slow and damages flash media. Plan:

1. Build the whole tree in a tmpfs directory (`/dev/shm/vdj-export-XXXX/`, or `mkdtemp` under `$XDG_RUNTIME_DIR`). Size check first against free RAM.
2. Verify in place: re-read with our own parsers (`pdb_parse_file`, `anlz_parse`) and compare counts against the input list.
3. Refuse unless the destination is an **empty** directory (the prompt requires this); never write anywhere else.
4. Copy to the destination in one pass: sequential writes, large buffers, files in a sensible order (PDB last so a half-written drive has no database), then `fsync` each file and `syncfs` once at the end. Audio is the bulk; `copy_file_range` or 1 MiB buffered writes.
5. Re-read from the destination and compare SHA-256 to the tmpfs copy.

"Single write" cannot be literally one write(2); the achievable meaning is: no random or repeated writes, each file written once, sequentially.

## Pipeline for a folder of audio

1. Scan `.wav`/`.mp3`; read tags (title/artist/album/genre/year/track no.) and duration, sample rate, bit depth, bitrate (the repo already has audio/ID3 code under `src/audio`; check before adding a dependency).
2. Analyse BPM and beat grid (needed for PQTZ/PQT2). The sync features in vdj-ui may already have a BPM detector; to confirm.
3. Generate waveforms: PWAV (preview, 400 entries), PWV2 (tiny), PWV3 (detail), PWV4 (colour preview), PWV5 (colour detail) for `.EXT`.
4. Assign ids (tracks, artists, albums, genres, artwork), build rows per table, lay out pages, write headers.
5. Write ANLZ DAT+EXT per track using `anlz_fake` or a new writer (`libcdj/src/anlz/anlz_fake.c` already emits PMAI, PPTH, PQTZ, PQT2, PCOB, PCO2 and waveform tags).
6. Copy audio into `Contents/`, write settings files, create playlists (one playlist per source folder is the obvious default).

## Proposed approach to the unknowns (in order)

1. **Round trip with no semantic change.** Write a PDB writer that re-emits the 7-track `export.pdb` from parsed rows, and diff against the original. Byte-identical output proves the page and row layout. This is the cheapest high-value test and needs no hardware.
2. Do the same for ANLZ with `anlz_fake` against the 7 real files.
3. Generate a new 1-track export by cloning a template row, test in the vdj-ui reader, then on the decks via the NFS path (the decks read the same files over the network, per the earlier prompts).
4. Only then test physical pendrives, with the single-write copy.
5. Determine which of `exportExt.pdb`, `RBFLTR.DAT`, `USBMNG.DAT`, `*SETTING.DAT`, `djprofile.nxs` are required by bisecting on a deck.

## Deck limits (implemented)

A deck loads the whole `export.pdb` into memory, so a pendrive with too many rows makes it run out of memory and misbehave. The limits come from the DJ community's experience with the players, not from a measurement of ours; **which deck model supports which limit is not known**, so the lower ones are the default.

| Rows of the database | Older decks (default) | Newer decks (`--raise-limits`, "Apply modern deck limits") |
|----------------------|-----------------------|------------------------------------------------------------|
| Tracks               | 10000                 | 20000                                                      |
| Artists              | 10000                 | 16000                                                      |
| Albums               | 10000                 | 16000                                                      |

What is counted is what the database will contain, as `buildPdb` numbers it:

- **Tracks:** distinct tracks over all the playlists of the export (a track on two playlists is one row).
- **Artists:** distinct non empty artist names (exact text). A track without an artist adds none.
- **Albums:** distinct (artist, album name) pairs with a non empty album name, so the same album name under two artists is two rows. A track without an album adds none.

Rules:

- The limits apply to **pendrive exports only**. The trakcrate library has no limits, however many tracks it holds.
- An export above the limit in force is **refused before anything is staged or written**, with the numbers and the way out: shorten the pendrive's lists in trakcrate (remove tracks, entries or whole playlists) and export again. At exactly the limit the export is allowed.
- The refusal comes first in the list of problems, so it is not hidden when many tracks have other problems.
- Above the *lower* limits but within the higher ones, the message adds that the modern limits could be applied. GUI: the export dialog shows the checkbox **Apply modern deck limits (...YMMV)** only when the lower limits are exceeded; ticking it raises the limits for that export. CLI: `trakcrate export --raise-limits` (also accepted by `trakcrate sync`). Above the higher limits nothing helps and the message does not offer it.
- Summary (`summariseExport`, used by the dialog) reports the counts and whether the lower and higher limits are exceeded; an update of an existing drive is checked the same way, against the whole database it would write.
- Code: `deckLimits`/`checkDeckLimits` in `src/trakcrate/exporter.cpp`, `lib/rblimits.c` in `src-cli/c/` (the same numbers and counting rule; both are tested).

## Risks and open questions

- Bad PDBs on a deck can show an unreadable-drive message; decks may also cache per-drive state. Keep the working pendrive and the known-good export as a baseline.
- Licensing and compatibility: the format is reverse engineered; no vendor spec. Cite the Deep Symmetry docs in code comments rather than copying.
- Where should this live: a new libcdj module (`src/pdbw/`) with a vdj-ui front end (menu: "Export folder to rekordbox pendrive") and a CLI tool for testing. The prompt does not say; core library changes need agreeing first (earlier instruction in `exporting-an-editable-pendrive.prompt.md`).
- Need from the user: confirm a spare pendrive can be formatted for destructive tests (exFAT/FAT32 vs. HFS+ is per-player), and which player models to target.

## Implemented (Phase 8): the staged export

`src/trakcrate/exporter.cpp`, driven from the trakcrate pane (**Export...** button, `src/ui/trakcrate_export_dialog.cpp`). The destination is a folder; other files on it (photos, `.Trash-1000`) are left alone, but it must not already have any of the four names an export writes (`Contents`, `PIONEER`, `SHA256SUMS`, `trakcrate-manifest.txt`, any case), and a failed export removes only those.

1. The playlists are gathered (a track in several playlists goes on the drive once); every track needs its audio, and its analysis unless "allow tracks that are not analysed" is set.
2. In a staging directory (`/dev/shm`, else `$XDG_RUNTIME_DIR`, else the system temp) the database, the ANLZ files, artwork and settings are built, then **checked there**: the database is read back with libcdj and compared with the plan, every ANLZ file must parse and name the right audio, the settings files must pass their CRC.
3. Everything is copied to the destination in one sequential pass, each file written once with 1 MiB writes, `fsync` per file and one `syncfs`: first the audio, then the other metadata, then `SHA256SUMS` and `trakcrate-manifest.txt`, and **`export.pdb` last**, so an interrupted export leaves no database. On failure or cancel everything written is removed again.
4. The destination is read back and every file compared by SHA-256.
5. The staging directory is always removed. Audio is streamed, never staged in memory.

Compatibility switches (the dialog's *Advanced* box, and `ExportOptions`): settings files, artwork, the PVBR / PWV4 / PWV5 tags, the checksum files, and copying `exportExt.pdb`, `RBFLTR.DAT`, `USBMNG.DAT` or `djprofile.nxs` from a real drive. They exist to find out, on the decks, which pieces a player needs (`UNKNOWN_BYTES.md` lists what is guessed). The manifest records the variant that was written. "Register as a virtual pendrive" adds the folder to the virtual pendrives, so the existing NFS export can serve it to the decks without a stick.

"Single write" means: no repeated or random writes, each file once, sequential, the database last; it is not literally one `write(2)`.
