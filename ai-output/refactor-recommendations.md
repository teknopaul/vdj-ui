# Refactor recommendations: code that could move into libcdj

General purpose library code belongs in `libcdj` (C, installed system-wide, usable by every tool). A lot of it currently lives in the vdj-ui C++ code
(`src/trakcrate/`), and that is fine for now. **Nothing here is to be fixed during the trakcrate CLI work** (`.planning/plans/trakcrate-cli_PLAN.md`);
this file only records candidates so the decision can be made later with the facts in front of us.

## How to maintain this file

While developing `src-cli/` (and whenever vdj-ui code is touched for another reason), add an entry when:

- code is written in `src-cli/c` that is not specific to the trakcrate CLI (a format reader/writer, an algorithm, a utility), or
- the same logic now exists twice (C++ in `src/trakcrate/` and C in `src-cli/c`), or
- the CLI needs something from libcdj that is missing, or reimplements something libcdj already has.

Keep each entry short; update or delete it when it is done or no longer true. Do not move code because of this file without the user asking.

Entry format: **what**, **where it is now** (file paths), **duplicated?**, **target in libcdj**, **notes** (API shape, tests that already exist, blockers).

- 2026-10-28 (CLI Phase 6): `import-rekordbox` duplicates `src/trakcrate/rb_import.cpp` (database to `meta.txt`, ANLZ to `beatgrid.txt`/`cuemarks.txt`/`waveform.bin`) in `src-cli/c/helper/cmd_rbimport.c`, split so bash keeps naming, dedupe and playlists. - 2026-10-28 (CLI Phase 5): the rekordbox writers now exist twice, in C++ (`src/trakcrate/{anlz_writer,pdb_writer,pdb_build,settings_files,settings_defaults,exporter,cuemark_render,artwork_paths}`) and C (`src-cli/c/lib/{rbanlz,rbpdb,rbsettings,rbexport,rbcue,artwork}.c`), plus the readers `rbdb.c` (libcdj based) used by `verify` and the staged check. The C export is byte identical to the C++ one (`test_export_oracle.sh`), so either is a faithful source for a libcdj `anlz_write.h` / `pdb_write.h`: the C side has no C++ or Qt in it, so it is the easier one to move. `rbpdb.c` (the page model, DeviceSQL strings, the builder) and `rbanlz.c` should go together; the builder needs a template `export.pdb`, which is now a third copy of `data/trakcrate/template-export.pdb` (`src-cli/script/usr/share/trakcrate/`): libcdj could ship the template as data. The JPEG encoder (`artwork.c`, ffmpeg's mjpeg) duplicates `src/ui/trakcrate_artwork.cpp` (Qt). `fsops.c` (`tc_find_audio`, `tc_mkdir_p`, `tc_rm_rf`) is small and general. `buf.h` (a growable byte buffer with LE/BE helpers) duplicates what every binary writer in libcdj's `anlz_fake.c`/`fake_pdb.c` does by hand. The export check in `verify` reads with libcdj (`<cdj/pdb.h>`, `<cdj/anlz.h>`) and so cannot disagree with it; `rb_roundtrip` (test only) is the executable form of the C++ round trip tests.
- 2026-10-28 (CLI Phase 4): the analysers now exist twice, in C++ (`src/trakcrate/audio_decode`, `analysis_beats`, `analysis_wave`, `analysis`) and C (`src-cli/c/lib/{decode,beats,wave}.c`, `helper/cmd_analyse.c`), proven byte identical on 8 synthetic tracks by `test_oracle.sh`. They need ffmpeg (decode only; `beats` and `wave` are pure C on a `struct tc_pcm`), so a shared home would be a small analysis library rather than libcdj core; `waveform.bin` read/write is now also in both. `src-cli/test/oracle/` is the only place where C++ is built from `src-cli/`: it exists to keep the two honest and goes away if the C++ analyser is ever replaced by the C one.
- 2026-10-28 (CLI Phase 3): the C format library now exists in `src-cli/c/lib/`: `fsutil` (safe names, atomic write, `tc_path_within`, the lock), `kv` (document with comments and order kept), `beatgrid`, `cuemarks`, `sha256`, `natsort`. Each has a counterpart in C++ `src/trakcrate/` (`track.cpp` KvDoc/BeatGrid/Cuemark, `sha256.cpp`, `natsort.cpp`, `fsutil.cpp`), and the kv/lock rules also in bash. `test_format_agreement.sh` checks bash and C read and write key/value files identically; there is no such cross-check against the C++ `KvDoc` yet (an obvious next step when it matters, e.g. a tiny C++ test driver reading the same sample files). The pure-C parts (no ffmpeg, no libcdj) are what would move into libcdj if the GUI ever shares them. One known difference: the bash writer keeps a `\r` on untouched lines of a CRLF file, the C writer normalises to LF.
- 2026-10-28 (CLI Phase 2): `src-cli/c/lib/kv.c` (print a `key: value` line with the format's escapes) and `lib/natsort.c` are the first real format code in C; both are small and general to the trakcrate format, candidates for a libcdj-side `trakcrate format` module if the GUI ever wants to share them. `helper/cmd_probe.c` (tags and cover via libavformat) duplicates `src/trakcrate/audio_probe.cpp`. The bash `tc_kv_get/tc_kv_set` (awk) in `common.sh` are a third implementation of the same key/value rules (C++ `KvDoc`, C `kv.c` print only). The lock (`.trakcrate-lock`) is implemented in bash (`tc_lock`) and in C++ (`trakcrate_scripts.cpp`).

## Settings sets (user-settings plan)

- `src/trakcrate/settings_sets.cpp` has its own small key/value reader and writer (`readKv`, `escapeValue`); `track.cpp` has another for `meta.txt`. A shared `kvfile` helper in `fsutil` would remove both copies, and `drive.txt` and `set.txt` could use it too.
- `TrakcratePanel::treeContextMenu` is now long (pendrive, playlist, folder, settings branches). Each branch could be a small function that fills the menu and returns its action table.
- The seven settings wrappers in `trakcrate_panel.cpp` (`createSettingsSet`, `renameSettingsSet`, ...) repeat the same lines. A helper taking a lambda would shorten them.
- The CLI (`src-cli/`) has no settings sets; porting `settings_sets` to the C helper would make both tools agree on `user-settings/<set>/`.
- `ExportOptions` still has both the settings byte fields and `settingsSet`; once callers stop passing bytes the fields could go.
