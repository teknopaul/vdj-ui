# Refactor recommendations: code that could move into libcdj

General purpose library code belongs in `libcdj` (C, installed system-wide, usable by every tool). A lot of it currently lives in the vdj-ui C++ code
(`src/trakcrate/`), and that is fine for now. **Nothing here is to be fixed during the trakcrate CLI work** (`.planning/plans/trakcrate-cli_PLAN.md`);
this file only records candidates so the decision can be made later with the facts in front of us.

## How to maintain this file

While developing `src-cli/` (and whenever vdj-ui code is touched for another reason), add an entry when:

- code is written in `src-cli/c` that is not specific to the trakcrate CLI (a format reader/writer, an algorithm, a utility), or
- the same logic now exists twice (C++ in `src/trakcrate/` and C in `src-cli/c`), or
- the CLI needs something from libcdj that is missing, or reimplements something libcdj already has.

Keep each entry short; update or delete it when it is done or no longer true. Do not move code because of this file without the user asking.

Entry format: **what**, **where it is now** (file paths), **duplicated?**, **target in libcdj**, **notes** (API shape, tests that already exist, blockers).

## Settings sets (user-settings plan)

- `src/trakcrate/settings_sets.cpp` has its own small key/value reader and writer (`readKv`, `escapeValue`); `track.cpp` has another for `meta.txt`. A shared `kvfile` helper in `fsutil` would remove both copies, and `drive.txt` and `set.txt` could use it too.
- `TrakcratePanel::treeContextMenu` is now long (pendrive, playlist, folder, settings branches). Each branch could be a small function that fills the menu and returns its action table.
- The seven settings wrappers in `trakcrate_panel.cpp` (`createSettingsSet`, `renameSettingsSet`, ...) repeat the same lines. A helper taking a lambda would shorten them.

## Sync improvements (2026-11-01)

Docs only, nothing was changed in libcdj. What the sync work found that belongs in or next to libcdj. Background: `doc/sync-timing.md`, `doc/sync.md`, `ai-output/sync-bpm-rounding.md`.

### libcdj behaviour worth fixing or extending

- **`v->master` is never cleared when another deck takes over, unless libcdj saw the matching request.** `vdj.c` (the `CDJ_STATUS` case, "if I am master, and now `v->master_req` matches his status") only drops `v->master` for a `master_req` it knows. After a master change made on the decks it stayed set. `onUpdate` in `src/network/network_manager.cpp` reported the VDJ as master on every status packet, so Sync could never follow the new master ("stuck after a few master changes"). The vdj-ui workaround: a deck flagged `CDJ_STAT_FLAG_MASTER` with `master_state == CDJ_MASTER_STATE_ON` wins over `v->master`. The proper fix is in libcdj: clear `v->master` when a status packet from another player says it is the master (`master_state ON`), and expose "who is master" as one value (`backline->master_id` is only ever set, never cleared).
- **A master-change callback.** vdj-ui gets the master from three places (`v->master`, the MASTER flag, `masterState`) and re-emits `masterChanged` on every status packet. libcdj could call a handler once per change with the old and new id. That would also remove the "deck left, no master" special case in `SyncController::deckLeft`.
- **Packet arrival time.** Beat callbacks have no timestamp, so vdj-ui reads `steady_clock` in the handler (`onBeat`, after the ALSA queue read). A receive time taken in the socket thread (`recvmsg` with `SO_TIMESTAMPNS`, converted to `CLOCK_MONOTONIC`) would take the scheduling delay between `recv` and the callback out of every `diff_ms`. It is the cheapest accuracy gain left and needs a `cdj_beat_packet_t` field or a callback argument.
- **Beat packet fields.** `cdj_beat_next()` (next-beat ms) is used; the field at 0x38 (`beat8_ms`, 8 beats ahead) is read by hand in vdj-ui (`data + 0x38`, big endian) and should be an accessor. The raw `cdj_beat_bpm()` / `cdj_beat_pitch()` are used by the telemetry. `cdj_beat_pitch` is truncated, not rounded (0.5 ppm, harmless, but a comment in libcdj would stop the next person checking).
- **Precision of the calculated BPM.** `cdj_calculated_bpm` returns a `float` (24 bit mantissa, about 0.00001 BPM at 140 BPM). Fine for sync, but `double` costs nothing (`ai-output/sync-bpm-rounding.md`).

### vdj-ui structure

- `src/ui/main_window.cpp` is now about 2560 lines. The sync part (`syncButtonPressed`, `startMasterSync`, `lockDiffLockTo`, the align state machine `startAlign` / `alignOnBeat`, `followLockedBpm`, `syncReferenceBpm`, `refreshDiffLock`, telemetry state, and the `beatTimed` lambda) could move to a `SyncCoordinator` QObject that owns `DiffLock`, `SyncController`, the per-deck `BeatTempo` / `BeatPhase` / `BpmChangeDetector` maps and the align state, and talks to the window through a few signals (`syncStateChanged`, `bpmRequested`, `nudgeRequested`). `MainWindow` would only connect them. That would also make the phase 5 to 9 behaviour testable without constructing a window (the tests that need a `MainWindow` today: `deckBeatsNudgeTheSequencer`, `syncIsAStickyModeAcrossMasterChanges`).
- The `beatTimed` lambda in `connectDeckSignals` does stashing, tempo, phase, difflock, alignment, controller, glide, telemetry and the measured-BPM label. Each of those is a short function on the coordinator.
- `DeckControls::setBpm` was feeding the BPM spinner's `valueChanged`, which meant "a deck's BPM was shown" and "the DJ typed a BPM" were the same event (every deck's BPM packet set the VDJ tempo while Sync was off). It is now blocked in `setBpm`; the cleaner shape is for the spinner to emit only on `editingFinished` / user actions, and for the model to be set through a separate setter.
- Tests that need a real ALSA sequencer skip when none exists (`QSKIP("no ALSA sequencer available")`); a fake `snd_seq` or a tempo model interface on `AlsaClock` would let `phaseShiftMs` and the nudge tests run everywhere.
- Build directory: the repo root has its own in-source `CMakeCache.txt` and `Makefile`, so `cmake ..` from a build directory regenerates the wrong tree. Moving the in-source build away (or an `.gitignore`/guard in `CMakeLists.txt` that refuses an in-source configure) would stop that mistake.

### Database editing and the exporters (from the add-to-rekordbox work)

- The pdb model, row encoders and ANLZ hash exist twice: C++ (`src/trakcrate/pdb_writer`, `pdb_build`, `pdb_append`) and C (`src-cli/c/lib/rbpdb.c`), kept equal by the export oracle test. They should live once, in libcdj (C), used by the GUI, the CLI and any other tool: the page model with parse and serialise, `loadDriveDb`, the appender, `analyzeSlot` / `analyzePartition`. That would also give libcdj a writer test fixture (`tests/fixtures/trakcrate/pdb-drive/`). Not necessary for any feature; the cost is that every format fact has to be fixed in two places (the CLI's ANLZ hash was missed for a week).
- `exporter.cpp` is now about 1450 lines: `gather`, staging, `copyOne` and the two engines (`exportDrive`, `addToDrive`) should be separate files (`gather.cpp`, `stage.cpp`, `copy.cpp`) behind an internal header. `rbexport.c` has the same shape (its `gather`, `copy_one` and staging are static), which is what stops the CLI from getting an `add-to-drive` command cheaply.
- `buildPdb` keeps the template's page counters for pages that did not change, so its header sequence can be lower than a page's counter (`loadDriveDb` only warns); setting the header sequence past the highest counter would make our files closer to rekordbox's.
- The index pages of a table are a count (`0x1fff0000 | n` at 0x38) followed by `(page << 3) | 3` entries, one per page with deleted rows (checked on two big sticks); `pdb-write-notes.md` still calls them undecoded. A reader that wants to list the pages with deleted rows can use them.
- `Library::addFolderToDrive` / `addPlaylistToDrive` now top up an existing virtual pendrive entry instead of making a duplicate; the CLI's `pendrive add` has no equivalent idea of entries.
- `TrakcratePanel::exportDrive` and `addToRekordbox` repeat the template loading, the artwork encoder lambda and the job wiring; one `startJob(ExportJob&&)` would remove ~40 lines.
- The C port of the add path (`src-cli/c/lib/rbadd.c`, `rbappend.c`) duplicates `exporter.cpp`'s `addToDrive` and `pdb_append.cpp` almost line by line, and `rbexport_internal.h` now exports `tcx_gather`, `tcx_stage_track_files` and `tcx_copy_one` from the exporter so that two engines can share them. Moving the pdb model, the row encoders, the drive database loader/editor and the ANLZ path hash into libcdj would let the GUI and the CLI call one implementation and would turn the three oracle tests (`test_export_oracle.sh`, `test_append_oracle.sh`, `test_add_oracle.sh`) into plain unit tests.
- `trakcrate export` writes `SHA256SUMS` and a manifest that `add-to-drive` (like the GUI's add) leaves alone, so `trakcrate verify` reports a stale checksum for `export.pdb` after an addition. Either the add path should rewrite both files when they exist (it would need to hash the new files), or `verify` should treat a checksum list older than `export.pdb.bak` as stale; the GUI has the same gap.
- The helper's `add-to-drive --stop-at STEP` (a test hook) and `AddOptions::stepHook` are two spellings of one idea; a shared list of step names in a header would keep them equal.
- The `copy_one` of `rbexport.c` creates files exclusively (an export into an empty folder) while `rbadd.c` has its own `copy_safe` (temporary name, fsync, rename), as `copyOne(..., update=true)` in C++; a single copy function with an `update` flag would remove one of them.
