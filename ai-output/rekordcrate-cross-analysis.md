# Cross analysis: our pdb / ANLZ knowledge vs rekordcrate

Written 2026-11-07. Read only: nothing in either code base was changed.

- **Ours:** `references/libcdj` (`src/anlz/anlz.c`, `src/nfs/pdb.c`, `doc-internal/rekordbox-anlz-format.text`, `rekordbox-db-format.text`), `src/trakcrate/*` (pdb writer/builder/appender, `ext_pdb`, `settings_*`, `anlz_writer`, `deck_edits`, `pqtz_offset.h`) and `doc/trakcrate/*` (`UNKNOWN_BYTES.md`, `pdb-write-notes.md`, `pdb-append-notes.md`, `usbanalz-hashing.md`, `settings-files.md`, `beat-grid.md`).
- **Theirs:** `~/github_workspace/rekordcrate` at commit `68cd702` (Rust, MPL-2.0): `src/anlz.rs`, `src/pdb/{mod,ext,string,offset_array,bitfields,io}.rs`, `src/setting.rs`, `src/device.rs`, `src/xml.rs`, `src/util.rs`, `src/xor.rs`, plus its test data in `data/`.

Method: I read both sides' type definitions and their comments, ran a tag survey (a throwaway Python scan, not committed) over rekordcrate's `data/` ANLZ samples, and checked our own sticks where a claim could be checked. "Verified" below means I checked it against bytes on this machine. "Claimed" means I only read it in their or our docs.

Both projects stand on the same upstream work (Deep Symmetry's `djl-analysis` and `crate-digger`, Henry Betts, flesniak's `python-prodj-link`), so the overlap is large. This report is about the differences.

### 2.3 Conflicts and things to check

1. **PCPT `status` (0x10).** Their doc: "4 if this cue is an active loop, 0 otherwise". Ours: 1 in all 530 entries, including 147 loops. They have a `Cue` struct with `status: u32` but the comment is inherited from the spec page. Our corpus contradicts the spec on every entry, so the spec value may only apply to certain rekordbox versions. Keep the raw value (libcdj already does).
2. **PQTZ header word.** Their comment "always 00800000" vs the bytes `00 08 00 00` in every file (theirs and ours). Not a real conflict; their comment has the nibbles swapped. The shift sits in the low half.
3. **PCOB 0x14.** They call it `memory_count`. In the file our deck wrote (`after-full`), the hot cue list (type 1, 3 cues) and the empty memory list (type 0) both have `ffffffff` there. So it is not a count of hot cues in the hot list. It may be a count of memory cues in the memory list when there are memory cues; we have no sample of memory cues in the corpus, so this is open, not decided.
4. **Index-page entries** (also in 3.3): they treat `IndexEntry = (page << 3) | flags` as a reference to a table page, with `num_entries` matching pages. Our `pdb-append-notes.md` found entries only for pages with deleted rows. One of the two statements is incomplete.

1. **Index pages.** They treat entries as page references; we saw entries only for pages with deleted rows. If every data page has an entry, our "one per page with deleted rows" is an artefact of what sticks we had.

## 6. Where the two approaches differ in design

- **Parse model.** Theirs is a typed parse-and-serialise model for ANLZ, pdb pages, strings and settings, with round trips asserted on real files. Ours is a C reader (libcdj) plus separate writers (`anlz_writer`, `pdb_build`, `pdb_append`) with a verbatim "raw page" fallback in the pdb model. The pdb model is as strict as theirs (byte-for-byte on 3 real files), the ANLZ side is not.
- **Unknown bytes.** They keep them as `unknown*` fields so a round trip preserves them. We copy from templates. For a track row both are the same in effect; for an ANLZ file only ours risks losing a tag we do not decode.
- **Sources of truth.** They rely on `djl-analysis` documentation and flesniak's work; we verify against files on this machine (counts such as "2162 files" in our docs). Where we disagree with the spec page (`PCPT.status`, `PQTZ` word) the disagreement is documented on our side only.
- **Writing for decks.** Only we have hardware-driven constraints: the path hash, the 4-byte alignment found by crashing a deck, `Contents/` naming, the sequence/`empty_candidate` rules, and the tmpfs→stick atomic switch. Their writers have never been shown to produce a stick a deck loads (none of their docs claims it).

### Later findings (2026-11-08)

- **Item 13 and the VBR loop pairs.** The upstream report was made by the user via GitHub before the VBR loop layout was known. That finding is new and not in it: for a loop on a variable bitrate mp3 the last four `PCPT` words are two pairs, start and end in 1/75 s, then start and end byte offset (their `unknown4..7`). Tested on a deck: loops play and draw on a VBR mp3, CBR not yet checked. The deck's own VBR byte offsets differ from our rule by 1-3 frames; both are mid-frame positions about 200 ms before the cue.
